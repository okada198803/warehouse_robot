# R0・R6:失敗の型 C・型 B のログ再解析(2026-10-19)

対象: multi/docs/multi/logs/*.jsonl(複数台の検証の経過ログ。新たな測定なし)。

**R0(型 C、6 件):事前の予想は外れた。**
- 6 件とも、最初の停止の時点で残りの目的地が `['shipping']` だけだった。南通路の経由地(中心 x=3.5)を通過済みのため、通路の候補から外れていた。
- `plan_executor.nearest_aisle()` は「まだ到達していない通路(queue 内)」だけを候補にする(通過済みの通路の誤登録を防ぐため)。そのため `near_aisle=None` → `cause=unlocated` となり、LiDAR の点数の確認(`scan_hits`)はそもそも行われていない(全件 `hits=None`)。
- 停止位置は南通路の中か入口付近(x 2.1〜4.7)。停止した相手は、経由地より東側にいた。
- 対照:同じ試行で、まだ南通路の経由地に着いていなかった r2 は `near=south_aisle`、`hits=164` で正しく登録できている。
- **結論:原因は認識(点数不足)ではなく、通路の特定の規則(経由地を通過したら、その通路を候補から外す)。** 停止ロボットの点数は、確認さえすればしきい値を十分に超えうる(r2 の例で 164 点)。

**R6(型 B、3 件):**
- 3 件とも Nav2 が `status 6`(中断)で失敗した。位置は南通路の北壁際(2.4〜2.9, 1.31〜1.44。通路の中心 y=1.05、幅 0.9 m のため壁は y≈1.5)、C2w #5 は西ホール(1.82, 2.1)。
- C1 stag #6 は、壁際で停止 → 通路を特定できず再試行 → 再試行の後に Nav2 が中断。C3 oppj #6・C2w #5 は、立ち往生の報告なしに Nav2 が中断した。
- 実行部は Nav2 の中断を最終的な失敗として扱い、再試行や回復をしない。
- **結論:壁際に寄った後の Nav2 の中断と、中断後に何もしない規則の組み合わせ。** 学習の前に、中断時のコストマップ消去と再試行(規則)、膨張半径の調整を試す余地が大きい。

**計画への影響:**
- M8 は「学習で認識すれば解決」ではなく、まず「通路の特定を、経由地でなく位置(通路の範囲に入っているか)で行い、LiDAR で確認する」規則の修正で検証できる。H5 の誤封鎖の再発は、LiDAR の確認(しきい値 16 点、誤検知 0/432)で防げる見込みで、R3 で確かめる。
- 学習による認識は、型 C の解決には必須でない。物体の種類による行動の選択(人なら待つ、パレットなら迂回)という、発展の問いで価値を測る。
- M9 も、まず規則(中断時の再試行・コストマップ消去)と設定の調整で検証し、残った失敗に対して学習を試す。
