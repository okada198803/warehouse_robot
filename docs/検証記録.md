## 2-6 の詳細と課題

- 検出: `status: blocked 入荷口 no progress; path seems blocked`(約 35 秒後)
- 再計画: LLM 案 1・2 は検証 NG、案 3(北通路)が検証 OK で採用
- 課題: 検証は「通行止めを通らないか」のみを確認しており、「最短かどうか」は確認していない。中央通路(約 7.5 m)は通行止めではないため、本来は中央を選ぶべきだった
- 課題: LLM の返答文と計画が食い違う例があった(例: 「北通路を通る」と言いつつ、南通路の経路を述べる)。返答文は検証対象外

## 実装上の注意(記録)

- パレット配置は `ros_gz create -string` だと SDF の `<` がシェルに解釈され失敗した。`-file` で SDF を一時ファイルに書き出す方式に変更して解消
- `pkill -f` は、コマンド行に検索文字列が含まれると自分自身を終了させる(`-x` でプロセス名指定に変更)
- `docker compose exec` は既定で root で実行される。ROS 2 のデータ通信は ubuntu ユーザーで行うため、`-u ubuntu` が必要

## 2-7 二重封鎖(中央パレット配置)の結果: 未達

- 南通路が通行止めの状態で `出荷口へ行って`。LLM は中央通路経由を計画し、送信(約 7.3 m)。
- 中央通路で `blocked`(no progress)を検出。中央を通行止めに追加。
- LLM の案 1〜3 は検証 NG。経路探索の迂回案として北通路経由を採用。
- 北通路で `no progress` が 2 回連続。北通路にはパレットがないため、中央パレット手前で物理的に詰まったと推定。
- 停止位置の判定が不正確(北通路を通行止めに「追加」する報告が出た)。
- 3 回の迂回で到着できず、`指示をください` で停止。

### 課題
- 物理的に詰まった後の回復がない(Nav2 の回復動作だけでは抜けられない)。
- `near_aisle` の判定が、実際の停止位置と一致しない場合がある。
- 検証は最短性を見ていないため、報告書には限界として記載する。

## 2-7 追加の検証(2026-10-10)

- 検証と実走の経路の不一致を修正: 送信計画に、検証で使った経路が通る通路を補う(`planner.py` の `_expand`)。テストは 15 件すべて成功。
- 中央通路への計画を送信したが、実行段階で停止。`plan_executor` の `no progress` で 3 回失敗。
- 停止の原因として、次を切り分けた。
  - パレットなしでも停止した(パレットが原因ではない)
  - 前進・回転の速度指令は両方動いた(物理的に動ける)
  - `/cmd_vel` の発行元に `behavior_server` が 5 つ。Nav2 の回復動作(その場回転・後退)が繰り返されていた
- 対策として、回転中は立ち往生としないよう `plan_executor` を修正(上限 24 秒)。`inflation_radius` を 0.35 → 0.25 に変更。
- 未解決: 停止位置の局所コストマップと DWB の候補経路の確認(RViz)。

## 2-7 最終結果(修正後): 合格

- 経路: 南通路で `no progress` → 後退 → 南を通行止めに追加 → 中央通路を再計画 → 中央で `no progress` → 後退 → 中央を通行止めに追加 → 北通路経由で出荷口へ到着(`status: done`)。
- 後退は直線、最大 4 m。通路中心から 2.5 m 離れた時点で停止し、停止時点の通路を `blocked` として報告する。
- 再計画上限は 3 回から 6 回に変更(早期中止の防止)。
- 回転中の判定は保留し、位置が動かない時間が 24 秒を超えたら停止とみなす。
- 計画の途中地点は、次の地点へ向かう向きに設定(入口でのその場回転を防止)。
- 検証で使った経路が通る通路を送信計画に補う(`_expand`)。
- 評価: 挙動に問題なし(ユーザー確認)。
