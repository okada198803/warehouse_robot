# 複数ロボット検証の設計(ブランチ multi-robot)

目的: 倉庫の通路で 2 台が行き合うときの課題を測り、改善案(C1〜C3)の効果を比較する。
単体構成の検証データ・コードは変更しない(タグ `freeze-2026-10-13`、`docs/auto/SHA256_freeze-2026-10-13.txt` で確認できる)。

## 条件
| 条件 | 内容 | 追加するもの |
|---|---|---|
| C0 | 協調なし(各ロボットが独立に動く) | なし。課題の洗い出し |
| C1 | 統制 LLM が全ロボットの状況を見て通路を割り当てる | 統制役(全台の位置・目的地・状態を入力) |
| C2 | 環境の工夫: 通路幅を広げ、通行方向を決める | 別ワールド(別 SDF・地図) |
| C3 | ロボット同士が通信し、通路の使用を宣言して経路を選ぶ | 通信(トピック)と経路選択ロジック |

C1〜C3 は、C0 で観察した課題に対応するものだけを足す(課題が出なければ足さない)。

## 構成(単体構成との差)
- 名前空間 `r1`, `r2`。Gazebo のトピックは `/<ns>/scan` など。TF・Nav2・map_server・plan_executor は台ごと。
- `ai_nav/multi_gen.py` が元ファイルから SDF・ブリッジ・Nav2 パラメータを `/tmp/pai_multi/` に生成する。元ファイルは書き換えない。
- `plan_executor.py`(凍結済み)は変更せず、起動ファイルでトピックを名前空間の中へ付け替える(`/ai/plan` → `/<ns>/ai/plan` など)。Mac 側は `host/ros_link_ns.py`(`ros_link.py` を継承)。
- 各ロボットは LiDAR で相手を障害物として見る(センサは台ごとに独立)。
- コンテナは `docker/compose.multi.yaml`(`name: pai_multi`、`pai-ros-multi`、noVNC 6081、rosbridge 9091)。`COMPOSE_FILE=compose.multi.yaml` で使う(`host/run_multi_auto.sh` が設定する)。単体構成の `docker/compose.yaml` は変更しない。単体構成のコンテナと同時に起動しない。

## 確認する前提(最初の動作確認)
1. `colcon build` が通り、`ros2 launch ai_nav multi.launch.py` で 2 台が現れる。
2. `/r1/scan`, `/r2/scan`, `/r1/odom`, `/r2/odom` が出る。
3. `/r1/ai/plan` で r1 だけが動き、`/r2/ai/plan` で r2 だけが動く。
4. 両台が南通路を逆向きに通る指示を出し、その結果(すれ違えるか、止まるか)を観察する。

## 単体構成との関係(変更の範囲)

## 追加シナリオ(2026-10-15 追記。測定前に記録した予想)
正面すれ違い(opp)に加え、相互に影響しうる 3 シナリオを同じ手順(各条件 10 試行、上限 150 秒、試行ごとに初期位置へ戻す)で測る。
opp の設定・データは変更しない(`SCENARIOS['opp']` は元の値、結果は C*.csv のまま。追加分は `C*_<シナリオ>.csv`)。

| シナリオ | 配置 | 条件 |
|---|---|---|
| same 同方向(追従) | r1: 入荷口 → 出荷口。r2: 座標 (1.1, 1.6) → 出荷口。どちらも最短は南通路(東向き) | C0・C1・C3・C2 |
| cross 交差(別の目的地) | r1: 入荷口 → 充電ステーション。r2: 事務所前 → 出荷口。どちらも中央通路(東向き)で、西ホールを逆向きに通る | C0・C1・C3(C2 は経路が南通路を通らないため対象外) |
| wait 通路内で待機中の台 | r2 は南通路の中央(3.5, 1.05)で 25 秒待ってから出荷口へ出発。r1: 入荷口 → 出荷口 | C0・C1・C3・C2 |

予想(測定前):
- same: 逆向きの組がないので C1・C3 の割り当ては C0 と同じ(両台とも南通路)になる。差が出るのは、同時進入で詰まるか、追従で済むか。C2 は両台が同じ車線を通る。
- cross: C1・C3 の規則は「同じ通路の逆向き」だけを見るため、ホールでの行き違いには効かない見込み。C0 と大きく変わらない。
- wait: C0 では r1 が待機中の r2 を障害物として確認し、南通路を通行止めに登録して中央通路へ回る(r2 が出発した後も記憶は残る)。C1・C3 は待機を知らないため C0 と同じ。C2(広い通路)は横を通れれば通行止めの登録が起きない可能性がある。
- 3 台の検証は行わない(報告書の 8-3 に課題として記載)。

## 追加シナリオその 2(2026-10-16 追記。測定前に記録した設計と予想)
最初の 4 シナリオ(opp・same・cross・wait)の測定で、次の弱点が見つかった。追加で補う。
- 全シナリオが固定の配置・固定のタイミングで、LLM も温度 0 のため、10 試行はほぼ同じ状況の再現である。
- 同方向(same)と待機(wait)は台間の初期距離が小さく(0.95 m・2.7 m)、「接触の可能性」(0.22 m 以下)が接触の目安にならない。
- 通路の途中での遭遇、同じ目的地の取り合い、停止し続ける台は未検証だった。

| シナリオ | 内容 | 条件 |
|---|---|---|
| stag 時間差の出発(逆向き) | opp と同じ配置で、r2 は 6 秒遅れて出発する(通路の途中で遭遇)。C1・C3 の協調は r2 の出発時に行う。走行中の r1 の計画は変えず、r2 だけが通路を選ぶ(C1 は中央が把握している各台の元の計画を渡す) | C0・C1・C3・C2 |
| dest 同じ目的地 | r1 は入荷口から、r2 は充電ステーションから、どちらも出荷口へ。先に着いた台が出荷口に留まる | C0・C1・C3(C2 は対象外) |
| dead 恒久停止の台 | r2 は南通路の中央で停止したまま(故障)。r1 は入荷口 → 出荷口。到着を求めるのは r1 のみ。通信できない台なので C1・C3 は協調できない | C0・C1・C3・C2 |
| oppj・samej・crossj・waitj | opp・same・cross・wait に、初期位置 ±0.15 m、向き ±0.3 rad、各台の出発遅れ 0〜5 秒のばらつきを加える。乱数は試行番号で固定し、条件間で同じ値を使う(対応のある比較)。協調は試行の開始時に行う | opp・same・wait は C0・C1・C3・C2、cross は C0・C1・C3 |

到着時間は、新シナリオでは各台の出発遅れを除いた値(CSV の t_net)で集計する。

予想(測定前):
- stag: C0 は通路の途中で出会い、後退・膠着で opp より成功率が下がるか、時間が延びる。C1・C3 は r2 の出発時に中央通路へ回るため、opp の C1・C3 と同程度の到着時間(約 35〜40 秒)になる。
- dest: 先に出荷口に着いた台が目的地を占有するため、後から着く台は到着できないか、大きく遅れる。C1・C3 の規則は「同じ通路の逆向き」しか見ないので、C0 と変わらない。
- dead: C0 は r1 が南通路の中で停止し、南を通行止めに登録(正しい登録)して中央通路へ回り到着する。C1・C3 は C0 と同じ。C2(幅 1.5 m)は、停止した台の横を通れれば通行止めの登録なしで到着する可能性がある。
- ばらつき(oppj など): 元のシナリオと同じ傾向だが、C0 では成否のばらつきが大きくなる。
- 3 台以上は実施しない(報告書の 8-3 に課題として記載)。
